[SIZE=6][B][FIX] Xiaomi Pad 5 Pro (elish) — full system freeze with Chrome on LineageOS 24.0[/B][/SIZE]

[B]Applies to:[/B] Xiaomi Pad 5 Pro (elish, M2105K81AC) running LineageOS 24.0
[B]Kernel:[/B] 4.19.325-cip136-st20 (LineageOS/android_kernel_xiaomi_sm8250, commit 6b34d2476532)

[SIZE=5][B]TL;DR[/B][/SIZE]

The kernel LineageOS 24.0 ships for elish is missing a cgroup freezer fix that LineageOS already applied to other 4.19 devices (a52q / a72q / gta4l, issue #756). Without it, opening Chrome can freeze the whole system until the watchdog reboots the tablet.

I backported the fix, built the kernel and I'm running it. The patch touches a single file and [B]does not change the kernel version string[/B], so the prebuilt vendor_dlkm modules keep loading — no loss of Wi-Fi, GPU or touch.

[SIZE=5][B]Symptoms[/B][/SIZE]

After some time using Chrome (easier to trigger with several tabs open), the tablet freezes completely: touch stops responding, audio hangs, and a few seconds later the device reboots by itself.

In pstore / the last kernel log you'll find something like:

[CODE]sysrq: Kill All Tasks[/CODE]

Sometimes instead of a reboot you just see the UI come back with system_server restarted (soft reboot to the lockscreen).

To check whether your tablet has the old crash recorded:

[CODE]adb root
adb shell grep -c "Kill All Tasks" /sys/fs/pstore/console-ramoops-0[/CODE]

[SIZE=5][B]Root cause[/B][/SIZE]

The 4.19 kernel uses the cgroup v2 freezer to freeze cached processes. The implementation in cgroup_leave_frozen() is outdated:

[CODE]	spin_unlock_irq(&css_set_lock);

	if (unlikely(current->frozen)) {
		/*
		 * If the task remained in the frozen state,
		 * make sure it won't reach userspace without
		 * entering the signal handling loop.
		 */
		spin_lock_irq(&current->sighand->siglock);
		recalc_sigpending();
		spin_unlock_irq(&current->sighand->siglock);
	}
[/CODE]

When leaving the frozen state races with vfork() or do_signal_stop(), the cgroup's nr_frozen_tasks counter and state can spuriously go to "unfrozen" while the task is still logically frozen. That task never re-enters do_freezer_trap(), so it stays stuck forever and the system hangs until the hardware watchdog resets the device.

The fix is the upstream implementation, already present in LineageOS/android_kernel_qcom_sm8150 (lineage-20, commit 7a05073b, "UPSTREAM: cgroup: prevent spurious transition into non-frozen state"), but [B]not[/B] in android_kernel_xiaomi_sm8250 (lineage-24.0) nor android_kernel_qcom_sm8250 (lineage-20).

[SIZE=5][B]What the patch does[/B][/SIZE]

It replaces the recalc_sigpending() block with JOBCTL_TRAP_FREEZE + TIF_SIGPENDING:

[CODE]	} else if (!(current->jobctl & JOBCTL_TRAP_FREEZE)) {
		spin_lock(&current->sighand->siglock);
		current->jobctl |= JOBCTL_TRAP_FREEZE;
		set_thread_flag(TIF_SIGPENDING);
		spin_unlock(&current->sighand->siglock);
	}
[/CODE]

This forces the task through do_freezer_trap() before it can return to userspace, so the spurious "unfrozen" transition can no longer happen.

[SIZE=5][B]Option 1 — Flash the prebuilt boot image (5 minutes)[/B][/SIZE]

[SIZE=4][B]1.1 Check compatibility FIRST[/B][/SIZE]

[CODE]adb shell getprop ro.lineage.version
# must be: 24.0-20261013-UNOFFICIAL-elish

adb shell uname -r
# must be: 4.19.325-cip136-st20-perf-g6b34d2476532[/CODE]

If your build is newer, [B]stop here[/B] and use Option 2. Flashing a kernel built from a different commit makes the vendor_dlkm modules fail to load (no Wi-Fi, no GPU, no touch).

Also confirm your slot:

[CODE]adb shell getprop ro.boot.slot_suffix
# _a or _b[/CODE]

The commands below use boot_a; replace with boot_b if your slot is _b.

[SIZE=4][B]1.2 Back up the current boot partition (do not skip)[/B][/SIZE]

[CODE]adb root            # or use "su -c" with Magisk
adb shell dd if=/dev/block/by-name/boot_a of=/sdcard/boot_stock.img
adb pull /sdcard/boot_stock.img[/CODE]

Keep that file. It is your rollback.

Grab boot_a_patched.img from the releases page:

[URL]https://github.com/tntgdh-beep/elish-kernel-fix/releases/tag/elish-24.0-20261013[/URL]

Size:   55078912 bytes[/CODE]

[CODE]adb reboot bootloader

fastboot reboot[/CODE]

First boot takes the usual 30–60 s.

[CODE]adb shell "dmesg | grep -iE 'version magic|disagrees about version|Unknown symbol'"[/CODE]

It should print nothing.

repack.py replaces [B]only the kernel[/B] — ramdisk, os_version and os_patch_level are kept from the stock image, and it re-reads the result to make sure it's correct. Then flash it as in step 1.4.

uname -r will [B]not[/B] change — that's intentional, it is what keeps the prebuilt modules loadable. Two reliable checks:

[SIZE=5][B]Troubleshooting[/B][/SIZE]

[B]Bootloop after flashing[/B] — restore the backup with fastboot flash boot_a boot_stock.img. Nothing else on the device was touched.

[B]No Wi-Fi / no touch / no GPU after booting[/B] — you flashed an image built from a different kernel commit. Restore the backup and rebuild with Option 2. Check with:

[CODE]adb shell "dmesg | grep -i 'version magic'"[/CODE]

[B]adb root says "adbd cannot run as root in production builds"[/B] — use Magisk:

[CODE]adb shell su -c "dd if=/dev/block/by-name/boot_a of=/sdcard/boot_stock.img"[/CODE]

[B]The freeze still happens[/B] — this fix only addresses the cgroup freezer bug. If your log shows a native system_server crash in BPF (tombstone with bpf / BPF_PROG_RUN frames), that is a different bug and is not fixed here.

[SIZE=5][B]FAQ[/B][/SIZE]

[B]Does it survive a LineageOS OTA?[/B]
No. Every OTA overwrites the boot partition. After updating, flash the image again — but only if the OTA's kernel is still commit 6b34d2476532; otherwise rebuild it.

[B]Is it safe / does it break SafetyNet?[/B]
Your bootloader is already unlocked and verifiedbootstate is already orange, so this changes nothing about the device's attestation state. The image is the stock ramdisk with a patched kernel.

[B]Does it change performance or battery?[/B]
No. It doesn't touch the scheduler, the freezer on/off logic or any tunable. It only fixes a race in the frozen → unfrozen transition.

[B]Can I use it on another sm8250 device?[/B]
Probably, but it was only tested on elish. Build it yourself with build-kernel.sh adapted to your device's defconfig — and don't flash the prebuilt image.

[B]Workaround without flashing[/B]
Disable the freezer (costs memory management performance, but stops the freezes):

[CODE]adb shell device_config put activity_manager use_freezer false
adb shell settings put global cached_apps_freezer disabled[/CODE]
